# R1855 — کنترل فایل ناموفق چاپ

علت قفل ظاهری: R1854 برای ثابت‌ماندن تنظیمات کل کارت را inert می‌کرد و handler حذف پس از ساخت پیش‌نویس برمی‌گشت. پیش‌نمایش و حذفِ عکس ناموفق نیز مسدود می‌شدند.

در R1855 فقط کنترل‌های تغییر مشخصات چاپ قفل می‌مانند؛ تصویر و دکمهٔ پیش‌نمایش قابل استفاده‌اند. پیش‌نمایش از اصل Blob موجود با thumbnail خواندنی ساخته می‌شود و اگر آماده نشود، حداکثر ۱۰ ثانیه بعد کنترل آزاد و خطا نمایش داده می‌شود؛ کیفیت فایل ارسالی تغییر نمی‌کند. فایلِ در دسترس نبودن اصل، اقدام انتخاب همان عکس را نمایش می‌دهد.

حذف از ارسال عملی صریح برای عکس تأییدنشده است. در صورت فعال بودن صف، درخواست‌ها ابتدا با AbortController متوقف و همهٔ درخواست‌های آغازشده جمع می‌شوند. سپس endpoint مالک/لابراتوار-محدودِ `POST /api/customer/uploads/:id/exclude`، زیر قفل سفارش و فایل، تنها pending را به deleted تبدیل می‌کند. درخواست تکراری امن است. فایل active و سفارش ثبت‌شده قابل حذف از این مسیر نیستند. اصل شیء در Object Storage پاک نمی‌شود و metadata حذف صریح در صف حفظ می‌شود.

شمارش نهایی فایل‌ها، deleted را کنار می‌گذارد؛ فاکتور/موجودی و دانلود همچنان از فایل‌های معتبر موجود استفاده می‌کنند. تکمیل JPEG هم به صورت شرطی pending→active انجام می‌شود تا پاسخ دیررس نتواند فایل کنارگذاشته‌شده را زنده کند. تأیید تکراریِ فایل active همچنان موفق است.

اگر آخرین فایل کنار گذاشته شود، صف خالی امکان انتخاب تازه می‌دهد. خطای حذف یا قطع اینترنت صف را پاک نمی‌کند. حذف از صف به معنای آزادکردن فضای Object Storage نیست؛ فایل‌های مشتری یا فایل‌های تأییدشده خودکار حذف نمی‌شوند.

هیچ migration یا تغییر قیمت، تعداد نسخه، مدل قاب/شاسی یا قوانین پرداخت وجود ندارد. تست‌های مرورگر (وب/موبایل/بستهٔ Windows)، idempotency/مالکیت API و PostgreSQL واقعی شامل حذفِ فایل ناموفق، حفظ موفق‌ها، ادامهٔ ارسال و جلوگیری از resurrection هستند. شناسهٔ انتشار: `2026-11-15-r1855-failed-photo-controls`.
