# Shared phone/password for photographer, lab and equipment store

A phone represents one owner across the three business roles. New roles reuse an existing identity and validate an existing base or enabled-photographer credential before sending ownership OTP. After successful OTP verification, a shared credential finalizer mirrors the chosen password to the existing users and photographer profiles for that normalized phone. Four signup completion paths use this finalizer. Existing records, IDs, memberships and financial references are not merged or moved. Historical duplicate IDs remain in place to preserve references; ambiguous duplicate memberships for the same portal still require administrative review.

No password/data bulk migration runs at deployment. On legacy split credentials, business login requires explicit owner recovery rather than allowing a photographer-only password to silently authorize a management role. A common account recovery action is available at login and registration and at /account-recovery.html. The existing SMS challenge/token flow is reused with a new `account` purpose. Migration 192 only extends the purpose CHECK constraint; it does not modify passwords or user records. Recovery completes after a locked, unexpired, unused verified challenge, and applies the new password to all records owned by that verified phone. Existing global/platform-admin credentials on that same verified phone follow the existing phone-owner recovery trust model too; no platform-admin role is created by recovery.

The shared finalizer locks by normalized phone, locks identities/profiles, rejects stale signup snapshots, mirrors the same server-generated password hash and revokes sessions on a real credential change or legacy convergence. Adding a role with an already common password keeps existing sessions. Forced owner changes and platform-admin self-service changes use the same finalizer, with expected-hash checks to reject stale changes. New accounts and new recovery passwords retain the eight-character minimum; existing verified legacy passwords can be reused when adding a role.

Lab staff cannot reset an owner's shared credential on behalf of that photographer. Lab administrative editing also cannot invent a separate password for an existing owner; ownership recovery is required. New lab creation by the platform admin reuses a matching coherent identity rather than adding a duplicate phone user. Photographer suspension/deletion remains role-scoped; lab deletion retains shared users, other role sessions and their audit actors. Existing lab business-data deletion behavior itself is unchanged.

The Windows login proxy does not forward unauthenticated password-reset calls. Instead of requiring another native installer, the recovery action in the existing Windows UI opens the same public HTTPS recovery page in the browser. Native expiry/offline queue/storage behavior is unchanged. The common UI is included before the final verified desktop UI snapshot.

Validation: 18 generated-handler/policy/client tests and five PGlite PostgreSQL-compatible database tests passed (23 total). These include all three real login handlers, all six role-addition orders, old split passwords, preserved IDs/reference histories, session behavior, stale password snapshots, replayed reset tokens, invalid/expired challenges, role denial, migration repeatability and desktop browser handoff. Server, UI bundle, common client and inline store-page JavaScript syntax were checked, and the transform ran twice. The previous R1391 tests also passed before the new transform, preserving pipeline ordering.

Full Docker/Liara deployment, production SMS delivery and real browser/Windows visual testing are not verified here. No live account, role, password, message or database was modified during preparation. This change replaces the uncommitted R1392 one-off photographer-to-lab promotion approach and is held for explicit publication under AGENTS.md authentication/security and schema stop conditions.
